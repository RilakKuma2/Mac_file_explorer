# 릴리즈 배포

앱은 Sparkle를 통해 GitHub Releases의 `appcast.xml`을 확인합니다. 새 버전을 알린 뒤 사용자가 버튼을 누르면 서명 검증 → 다운로드한 앱 설치 → 재실행을 진행합니다. 기본 확인 주기는 하루이며, 앱 메뉴에서 수동 확인 또는 자동 확인 해제가 가능합니다.

## 새 버전 올리기

1. `Resources/Info.plist`의 표시 버전과 내부 빌드 번호를 올립니다. 첫 공개 버전은 `0.1`입니다. 내부 빌드 번호는 사용자에게 보이는 버전과 별개로 항상 증가시킵니다.
2. `swift test`를 실행하고 변경 사항을 커밋·푸시합니다.
3. 최초 업데이트 키가 저장된 Mac에서 `./scripts/prepare-release.sh`를 실행합니다.
4. GitHub에서 해당 커밋으로 **일반 릴리즈**를 만듭니다. 태그는 `v0.1`처럼 앱 버전과 일치해야 합니다.
5. `dist/releases/v0.1/`의 **DMG, 업데이트용 ZIP, `appcast.xml`을 함께** 첨부하고 Latest로 지정합니다. 일반 설치에는 DMG를 안내합니다.

앱 ZIP만 올리거나 소스 코드만 푸시해서는 업데이트가 제공되지 않습니다. 초안·프리릴리즈는 일반 사용자의 업데이트 대상으로 사용하지 않습니다. 서명된 XML이나 ZIP은 생성 후 편집하지 마세요. 릴리즈 전에 별도 앱 사본으로 이전 버전 → 새 버전 업데이트를 확인하세요.

빌드는 실행한 Mac의 아키텍처를 대상으로 합니다. 현재 배포 준비 환경은 Apple Silicon(`arm64`)입니다. Sparkle는 생성한 앱의 시스템·아키텍처 요구사항을 피드에 기록합니다. Intel 배포는 별도의 빌드와 피드 검증이 필요합니다.

## 서명 키

- 업데이트용 Ed25519 개인 키는 macOS 키체인의 `app.macexplorer.filemanager` 계정에 보관합니다. 공개 키만 `Info.plist`에 포함됩니다.
- 키를 Git, 릴리즈 첨부 파일, 로그에 올리지 마세요. 기존 키를 잃으면 기존 설치본에 업데이트를 배포하지 못할 수 있습니다. 키체인과 키의 안전한 백업을 유지하세요.
- GitHub Actions 배포를 도입할 경우 서명 키와 코드 서명 인증서를 별도 Secrets로 구성해야 합니다. 현재 스크립트는 로컬 키체인을 사용하며, 자동으로 릴리즈를 게시하지 않습니다.
- 기본 빌드는 로컬 자체 서명입니다. 공개 배포의 Gatekeeper·공증은 Sparkle 업데이트 서명과 별개이며, Developer ID 서명과 공증은 별도로 구성해야 합니다.

Sparkle 라이선스는 배포 앱의 `Contents/Resources/Sparkle-LICENSE`에 포함됩니다.
